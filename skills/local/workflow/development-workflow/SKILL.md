# Development Workflow

使用一条可伸缩的主流程完成软件开发任务。领域技能负责提供专业知识，本技能负责控制执行顺序、改动边界和完成标准。

## 核心原则

1. **结果优先**：先明确用户要得到的行为或结论，再决定采用多少流程。
2. **证据先于修改**：先读取现状、复现问题或找到现有模式，不凭印象编辑。
3. **最小完整改动**：只修改实现目标所需的内容，同时完成必要的测试、类型和文档同步。
4. **保护用户现场**：保留未关联的工作区改动，不执行未经授权的破坏性 Git、发布或外部写入操作。
5. **按风险验证**：验证强度与变更风险成正比，不把完整测试套件机械地用于每个文本改动。
6. **完成后再交付**：只要仍有安全且相关的验证或收尾步骤，就继续完成，不把半成品交给用户。

## 1. 判断任务模式

先根据用户请求确定允许的动作：

| 模式 | 默认行为 |
|---|---|
| 回答或解释 | 读取必要上下文并回答，不修改文件。 |
| 诊断 | 复现并说明根因；除非用户同时要求修复，否则不实施修改。 |
| 评审 | 检查差异和风险，按严重程度报告；除非明确要求，否则不改代码。 |
| 修改或构建 | 实现请求、验证行为并完成相关收尾。 |
| 发布、部署或破坏性操作 | 仅在用户明确授权且范围清楚时执行。 |

新消息如果明显替换了原请求，停止旧方向；如果是补充要求，将两者合并处理。

## 2. 建立事实基线

编辑前完成与任务相关的最小调查：

- 阅读仓库级和目录级指令文件。
- 检查工作区状态，识别并保护已有改动。
- 查看项目结构、依赖、构建与测试命令。
- 用快速搜索定位实现、调用方、类型、测试和文档。
- 读取足够上下文，确认约定和现有模式。
- 涉及版本、外部 API、安全规则或近期可能变化的事实时，查阅权威来源。

不要为了“全面了解”无目的地读取整个仓库。调查应当回答具体问题，并在获得足够证据后进入下一步。

## 3. 按复杂度规划

采用最轻量但足够可靠的计划形式：

### 简单任务

适用于范围明确、影响局部、验证方式直接的单文件或小型修改。无需创建计划文件，调查后直接实现并验证。

### 中等任务

适用于多文件修改、存在依赖顺序或需要多个验证步骤的任务。使用 Agent 自带的计划能力记录少量可验证步骤，并保持同一时间只有一个步骤进行中。

### 复杂或长周期任务

适用于跨模块改造、研究、迁移或可能跨会话继续的工作。明确记录：

- 目标和不做什么。
- 关键假设与待确认问题。
- 依赖顺序和风险点。
- 每阶段的验收与验证方式。

只有用户要求持久计划，或任务确实需要跨会话恢复时，才将计划写入 `.planning/<task-id>/`。不要默认在项目根目录生成 `task_plan.md`、`findings.md` 或 `progress.md`。

如果缺失信息不会改变总体方向，采用合理假设继续并说明。只有某个选择会显著改变结果、成本、风险或外部影响时才暂停询问。

## 4. 根据任务类型建立证据

### 缺陷修复

1. 复现问题或建立可观察的失败证据。
2. 定位根因，不把症状当根因。
3. 选择能防止复发的最小修复。
4. 在适合的层级增加回归测试。

无法可靠复现时，明确已有证据、推断和仍未知的部分。

### 新功能

1. 明确用户可观察的结果和验收条件。
2. 找到项目中最接近的既有实现。
3. 识别接口、数据、错误状态和兼容性影响。
4. 按可运行、可验证的完整切片实现。

### 重构

1. 先确认需要保持不变的行为。
2. 运行或定位覆盖该行为的测试。
3. 分离行为变更和结构整理。
4. 用测试、类型或等价输出证明行为未变。

### 文档或配置

核对名称、路径、命令和当前实现。运行格式、解析、语法或配置加载检查；没有行为变化时不强制编写测试。

### 代码评审

优先检查正确性、回归、数据安全和缺失验证。结论必须能指向具体代码和触发场景；没有可执行问题时明确说明。

## 5. 实施改动

- 遵循仓库现有架构、命名、类型和测试风格。
- 优先复用已有抽象；只有重复已经真实存在时才增加新抽象。
- 保持补丁聚焦，不顺手重构无关代码或批量格式化。
- 同步更新受影响的测试、类型、文档和配置。
- 对用户输入、鉴权、持久化、外部调用和 shell 边界进行针对性安全检查。
- 对数据库或公共接口采用兼容、可回滚的渐进迁移。
- 使用其他领域技能时，只加载完成当前任务真正需要的最小集合。

可以并行执行互不依赖的读取、检查或验证，但共享文件、依赖链和破坏性操作必须保持有序。是否使用子 Agent 由宿主规则和任务收益决定，不把并行本身当作目标。

## 6. 分层验证

从最接近改动的证据开始，再根据风险扩大范围：

1. **目标验证**：相关单元测试、复现步骤、解析器或最小命令。
2. **静态验证**：类型检查、lint、格式或语法检查。
3. **集成验证**：相关模块、构建、集成测试或端到端流程。
4. **运行时验证**：浏览器、UI、网络、日志或真实交互；仅在任务需要时执行。
5. **变更审查**：检查 diff 和工作区状态，确认没有遗漏、调试残留或无关文件。

若无法运行某项验证，说明具体原因和剩余风险。不要把“看起来正确”描述为已经验证。

验证失败时先诊断原因，再调整方法。不要不加变化地重复同一失败操作。连续尝试仍受同一外部条件阻塞时，汇总证据并请求用户处理该条件。

## 7. 交付前自审

只检查与本次任务相关的维度：

- 是否满足用户可观察的结果。
- 是否遗漏调用方、类型、错误路径或边界情况。
- 是否影响兼容性、数据、安全、性能或可回滚性。
- 测试是否真正覆盖变更，而不是仅仅通过。
- 是否保留用户原有改动并避免扩大范围。
- 文档与实现是否一致。

发现问题时先修正并重新验证，再交付。

## 8. 清晰交付

最终回复优先说明结果，然后简要列出：

- 完成了什么。
- 关键实现或设计选择。
- 实际运行的验证及结果。
- 尚存风险、未执行项或需要用户决定的下一步。

不要把工具调用流水账当成交付说明，也不要声称执行了没有运行的测试、提交、推送或部署。

## 完成标准

任务只有在以下条件满足时才算完成：

- 用户要求的结果已经实现或问题已经回答。
- 相关验证通过，或无法验证的原因已明确记录。
- 没有遗留明显的临时代码、断链或未解释失败。
- 工作区中的用户改动得到保护。
- 外部副作用没有超出授权范围。
- 最终说明准确、简洁且可复核。
